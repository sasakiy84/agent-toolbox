# Sasakiy Changelog

`CHANGES.md` を追加・修正・レビューするときに使う。まずリポジトリの `AGENTS.md` と既存 `CHANGES.md` を読む。リポジトリ固有の見出し順、サブセクション、担当者表記がある場合はその形式に合わせる。

## 基本方針

- 未リリースの変更は `## develop` に追記する。
- リリース時は `## develop` を `## <バージョン>` に変更し、必要に応じて `**リリース日**: YYYY-MM-DD` を記載する。
- 変更履歴は派生元ブランチとの最終的な差分だけを書く。
- 開発ブランチ内の中間状態の修正、表記ゆれ修正、後から同じブランチ内で打ち消された変更は原則として書かない。
- `CHANGES.md` が存在しない場合は、勝手に作る前にリポジトリ固有の規約を確認する。

## 種別

種別は以下の 4 つを使う。

- `[CHANGE]`: 後方互換のない変更。
- `[ADD]`: 後方互換がある追加。
- `[UPDATE]`: 後方互換がある変更。
- `[FIX]`: バグ修正。

種別の順番は `CHANGE` → `ADD` → `UPDATE` → `FIX` にする。リポジトリ固有の `AGENTS.md` が別の順序を明示している場合は `AGENTS.md` を優先する。

## エントリ形式

基本形:

```markdown
- [UPDATE] Sora C++ SDK を `2026.2.0-canary.14` に上げる
  - libwebrtc のバージョンを `m150.7871.0.0` に上げる
  - @torikizi
```

ルール:

- エントリは `- [種別] 変更内容を〜する` の形で書く。
- 変更内容は日本語で書く。
- 担当者行はエントリの最後に置く。
- 担当者行は `  - @ユーザー名` の形で、本文より 2 文字分インデントする。
- 複数の補足が必要な場合は、担当者行の前にサブリストで書く。
- 仕様、原因、対処、未対応、影響範囲などが重要なバグ修正では、サブリストで具体的に書く。

## misc

機能に直接影響しない変更は、`### misc` に置く。対象例:

- ドキュメント追加や整理。
- CI/CD、GitHub Actions、pre-commit / prek、lint、format、typecheck の変更。
- ビルド・パッケージング・公開フローの変更。
- 内部リファクタリングやテスト整備で、利用者向け機能に直接見せる必要が薄いもの。

`CHANGES.md` がコンポーネント別サブセクションを持つ場合は、該当コンポーネントに入れる。どこにも属さないものを `misc` に入れる。

## 書くべき内容

以下は通常 `CHANGES.md` に書く。

- 公開 API、CLI、設定、ファイル形式、出力形式、依存バージョンなど、利用者が観測できる変更。
- 後方互換のない変更。
- 新機能や新オプション。
- バグ修正。
- リリース成果物、パッケージング、CI、対応プラットフォームに影響する変更。
- 未対応事項や制限を明示する必要がある修正。

以下は通常書かない。

- 同じ開発ブランチ内で完結した一時的な修正。
- 最終差分に残らない変更。
- issue の磨き上げだけで、製品やリポジトリ成果物に影響しないもの。
- コードコメントやテスト内部だけの微修正。ただしリポジトリ固有の規約で misc に書く場合は合わせる。

## develop セクションへ追記する

1. `AGENTS.md` と `CHANGES.md` の `## develop` を読む。
2. 変更が利用者向けか、`misc` か、書かないべき中間状態かを判断する。
3. 種別を `CHANGE` / `ADD` / `UPDATE` / `FIX` から選ぶ。
4. 種別順とサブセクション構成に合わせて挿入する。
5. 担当者行を最後に付ける。担当者が分からない場合は関連コミットや issue の担当者を確認し、根拠がなければユーザーに確認する。
6. issue 対応なら、issue の完了条件と `CHANGES.md` エントリが一致しているか確認する。

## リリースセクション

リリースセクションは次の形式にする。

```markdown
## 2026.2.0

**リリース日**: 2026-01-27
```

既に表記ゆれがある場合でも、過去セクションを不用意に一括修正しない。新しいセクションはリポジトリ固有の直近形式に合わせる。

## レビュー観点

`CHANGES.md` をレビューするときは以下を見る。

- 種別が内容に合っている。
- 種別順が崩れていない。
- `misc` に入れるべきものがトップ階層に混ざっていない、または逆に利用者向け変更が `misc` に埋もれていない。
- 担当者行が最後にあり、インデントが揃っている。
- 変更内容が最終差分を表しており、中間状態の説明になっていない。
- issue 本文やコミット内容と矛盾していない。
- リリース済みセクションを不必要に書き換えていない。
