# 技術書執筆ガイドライン

このリファレンスは、技術解説を「読者の理解が進む道筋」として設計するために使う。

## 1. 目的

目指す文章は、読者が手順をなぞるだけでなく、次を説明できる状態にする。

- なぜその技術が必要なのか。
- どの概念を区別すべきか。
- どの例が本質を示しているのか。
- どの選択肢にどのトレードオフがあるのか。
- どの場面で使い、どの場面で避けるのか。

## 2. 主要な説明パターン

### 2.1 誤解から入る

読者が抱きそうな誤解や違和感を入口に置く。

流れ:

1. 読者の素朴な理解を提示する。
2. その理解では説明できない現象を示す。
3. 正しい定義や見方を提示する。
4. 小さな例で確認する。
5. 実務上なぜ重要かを述べる。

テンプレート:

```md
[技術] を [ありがちな理解] と捉えると、最初は理解しやすいかもしれません。
しかし、その理解のままだと [説明できない現象] を説明できません。
正しくは、[正しい見方] と捉える必要があります。
まずは、次の最小例でその違いを確認します。
```

悪い例:

```md
この構文は便利な記法です。コンパイラによって通常のコードに変換されます。
```

よい例:

```md
この構文を「専用のテンプレート」と考えると、最初は理解しやすいかもしれません。
しかし、その理解のままだと、なぜ通常の式や関数と組み合わせられるのかを説明できません。
正しくは、通常のコードへ変換される構文拡張として見る必要があります。
```

### 2.2 地図から入る

要素技術が多いテーマでは、個別説明の前に領域を分類する。

流れ:

1. 技術領域が複雑化した背景を説明する。
2. 領域を大きな分類に分ける。
3. それぞれの関心事を列挙する。
4. この章で扱う範囲を宣言する。
5. 後続の節が分類のどこに位置するかを示す。

テンプレート:

```md
[領域] を一枚岩として扱うと、[用語A]、[用語B]、[用語C] が同じ平面に並んでしまいます。
しかし、それぞれが解決しようとしている問題は異なります。
そこで本章では、まず関心事を [分類1]、[分類2]、[分類3] に分けます。
この分類を先に作っておくことで、後で登場する個別の仕組みを迷子にせず理解できます。
```

### 2.3 トレードオフから入る

複数の選択肢があるテーマでは、単一の正解を押しつけない。

流れ:

1. 現実の要求を提示する。
2. 単純な理解が崩れる条件を示す。
3. 複数の選択肢を比較する。
4. 長所、短所、前提条件を説明する。
5. 「何を犠牲にして何を得るか」を言語化する。

テンプレート:

```md
[手法A] は [利点] を得る代わりに、[負担] を引き受けます。
[条件] ではこの負担は小さいため、[手法A] は有効です。
一方で、[別の条件] では [負担] が支配的になるため、[手法B] を検討します。
```

### 2.4 定義から実装へ降りる

似た用語が混同されやすいテーマでは、先に定義を固定する。

流れ:

1. 混同されやすい用語を取り上げる。
2. 本文内での定義を明示する。
3. 状態遷移やモデルで抽象化する。
4. 小さな異常例を示す。
5. 実装上の仕組みに降りる。
6. 高レベルの API や設計指針に戻す。

テンプレート:

```md
[用語A] と [用語B] は、日常的には同じ意味で使われることがあります。
しかし本章では区別します。[用語A] は [定義A]、[用語B] は [定義B] です。
この区別を先に置く理由は、後で [誤解しやすい判断] を正確に説明するためです。
```

### 2.5 仕組みと運用を接続する

仕様や手順を理解するだけでは不十分なテーマでは、運用、失敗、互換性まで含める。

流れ:

1. その仕組みが解決する現実の問題を述べる。
2. 主目的だけでなく、互換性、性能、運用性も示す。
3. 手順を段階に分ける。
4. 各段階で何が保証され、何がまだ保証されないかを説明する。
5. 歴史的な失敗や攻撃を紹介し、設計理由を補強する。
6. 設定、実装、運用上の判断へ落とす。

テンプレート:

```md
[仕組み] の目的は、単に [表面的な目的] を満たすことではありません。
[保証1]、[保証2]、[互換性や運用上の要求] も同時に満たす必要があります。
したがって手順を読むときは、[内部処理] だけでなく、どの時点で何を信用できるようになるかに注目します。
```

## 3. 章構造テンプレート

### 3.1 章タイトル

章タイトルは、扱う技術名だけでなく、読者が得る理解を含める。

弱いタイトル:

```md
第4章 [技術名]
```

強いタイトル:

```md
第4章 [技術名] で [読者ができるようになる判断] を理解する
```

### 3.2 章冒頭

章冒頭では次を 800 字程度までで提示する。

- いま読者がどこにいるか。
- この章で扱う問題は何か。
- その問題が実務でなぜ重要か。
- この章で扱う範囲と扱わない範囲は何か。
- 読み終えると何を判断できるか。

テンプレート:

```md
前章では、[前章の到達点] を見ました。しかし、[前章の方法] だけでは [新しい問題] を扱えません。
本章では、[中心トピック] を使って、この問題を [観点] から整理します。

最初に [用語またはモデル] を定義し、次に [最小例] で問題を再現します。
その後、[仕組み] を説明し、最後に [実務上の判断] をまとめます。
本章の目的は、[技術名] の API を暗記することではなく、[読者ができるようになる判断] です。
```

### 3.3 節構造

節は次の順番で書く。

1. 問いを置く。
2. 用語を定義する。
3. 最小例を出す。
4. 仕組みを説明する。
5. 例外、落とし穴、限界を述べる。
6. 次の節へ接続する。

テンプレート:

```md
#### なぜ [技術/概念] が必要なのか

[読者がすでに知っている方法] でも、[単純なケース] では問題ありません。
しかし、[条件] が加わると [失敗] が起こります。

ここで [技術/概念] が必要になります。[技術/概念] とは、[短い定義] です。
まずは次の例で、[失敗] がどのように起こるかを見ます。
```

### 3.4 章末

章末のまとめは、章冒頭で立てた問いに答える。

弱いまとめ:

```md
本章では [技術] について説明しました。
```

強いまとめ:

```md
本章では、[技術] を [単純な見方] ではなく、[正しい見方] として整理しました。
最初に [問題] を確認し、次に [仕組み] を見ました。
この理解に立つと、[実務上の判断] も説明できます。
次章では、この考え方を [次のトピック] に広げます。
```

## 4. 文体ルール

- 原則として `です・ます` または `だ・である` のどちらかに統一する。
- 実務書、入門書、チーム向け教材では `です・ます` を使いやすい。
- 理論寄り、仕様寄り、定義中心の文章では `だ・である` を使いやすい。
- 本文は `です・ます`、定義ボックスは `である`、対話文は口語のように、役割が違う場合だけ混在させる。
- 一文は 40-80 字程度を基準にする。
- 長文は原因と結果、前提と結論、定義と例、一般論と例外で分ける。

接続語の使い分け:

- 定義する: `ここでは`, `本章では`
- 理由を述べる: `なぜなら`, `その理由は`
- 対比する: `一方で`, `これに対して`, `しかし`
- 言い換える: `つまり`, `言い換えると`
- 例を出す: `たとえば`, `具体的には`
- 注意する: `ただし`, `なお`, `ここで重要なのは`
- 進める: `ここまでを踏まえて`, `次に`, `最後に`

## 5. 情報の出し方

### 5.1 先に地図を渡す

複雑な章では、個別の API や設定に入る前に地図を渡す。

地図の種類:

- 領域の分類
- 処理の流れ
- 責務の分離
- 時間の流れ
- レイヤー
- 比較軸

### 5.2 用語は初出時に定義する

テンプレート:

```md
[用語] とは、[短い定義] です。直感的には、[身近な言い換え] と考えるとよいでしょう。
たとえば、[具体例] が [用語] にあたります。
```

### 5.3 例は最小から始める

最初の例に実務コードをそのまま出すと、読者は本質以外の情報に気を取られる。まず、失敗や仕組みが見える最小例にする。

悪い例:

```md
認証、キャッシュ、エラーハンドリング、ルーティング、表示制御が全部入った例から始める。
```

よい例:

```md
入力、変換、出力だけが見える最小例から始める。
その例で何が起きるかを確認してから、非同期処理、共有状態、エラー処理へ進む。
```

### 5.4 歴史は設計理由を説明するときだけ使う

歴史的経緯は、設計の必然性を説明するときに使う。年表そのものを目的にしない。

よい使い方:

```md
当時の主流の方法には [制約] がありました。その制約を避けるために、[新しい設計] は [別の方向] を選びました。
この背景を知ると、現在の API が一見遠回りに見える理由を説明できます。
```

## 6. コード例の書き方

### 6.1 差分で学ばせる

1. 動く最小コードを示す。
2. 問題を 1 つ発生させる。
3. 変更箇所だけを示す。
4. なぜその変更で直るかを説明する。
5. 残る問題を次の節へ渡す。

### 6.2 コード直後に読むポイントを書く

```md
注目するのは、[コード上の差分] です。
[条件] の場合、[理由] によって [結果] になります。
```

### 6.3 実務コードに進む前に制約を書く

```md
ここでは説明を簡単にするため、[省略した要素] は省略しています。
実際の画面やシステムでは、少なくとも [追加すべき要素] を検討する必要があります。
```

## 7. 注、警告、コラム

### NOTE

本文の理解を助ける補足に使う。

```md
> NOTE
> 本章では [範囲] だけを扱います。[範囲外] では同じ用語でも意味が変わる場合があります。
```

### WARNING

誤るとバグ、脆弱性、データ破壊につながる点に使う。

```md
> WARNING
> [設定や実装] を不用意に使うと、[具体的な危険] が起こる可能性があります。
> [判断基準] を踏まえて決める必要があります。
```

### コラム

本文の主線から外れるが、理解を深める背景に使う。

使ってよい内容:

- 歴史的経緯
- 名前の由来
- 代替技術との関係
- 仕様策定の背景
- 実務でよくある逸話

使わない内容:

- 本文に必要な定義
- 章の結論
- 安全上の注意
- 手順の必須ステップ

## 8. 章立てサンプル

### 8.1 基礎から実装へ進む

```md
第1章 開発対象の全体像
  1.1 なぜ実行環境を理解する必要があるのか
  1.2 依存関係とビルド工程の役割
  1.3 開発時と本番時で何が変わるのか
  1.4 まとめ

第2章 言語と実行モデルを理解する
  2.1 値、参照、オブジェクト
  2.2 関数とクロージャ
  2.3 非同期処理とイベントループ
  2.4 後続のコードを読むために必要な考え方

第3章 宣言的な記述で構造を表現する
  3.1 なぜ専用の記法が必要なのか
  3.2 記法はどのように通常のコードへ変換されるか
  3.3 属性と子要素
  3.4 リスト、条件付き処理

第4章 内部状態と外部同期を分ける
  4.1 入力値と内部状態の責務
  4.2 状態更新と再計算
  4.3 外部システムとの同期
  4.4 状態を持たない設計を選ぶ
```

### 8.2 境界と脅威から始める

```md
第1章 守る対象と境界を分ける
  1.1 システムを構成する主体と通信経路
  1.2 提供側で守るもの
  1.3 利用側で隔離するもの
  1.4 通信経路で保証するもの
  1.5 本書で扱う攻撃者モデル

第2章 境界による隔離
  2.1 論理的な境界が守るもの
  2.2 境界を緩和する条件
  2.3 入力が境界を破るしくみ
  2.4 実行可能な操作を制限する

第3章 資格情報を安全に扱う
  3.1 資格情報が自動送信される意味
  3.2 読み取り、送信、利用範囲の制御
  3.3 偽装リクエストと固定化
  3.4 認証フローと設定のトレードオフ
```

### 8.3 比較軸で進める

```md
第1章 システムに求められる性質
  1.1 信頼性とは何か
  1.2 スケーラビリティをどう測るか
  1.3 メンテナンス性を設計に含める
  1.4 単一のツールでは足りない理由

第2章 保存と検索の基本構造
  2.1 単純な方法
  2.2 読み取りに強い方法
  2.3 書き込みに強い方法
  2.4 書き込み、読み取り、容量のトレードオフ

第3章 複製と遅延
  3.1 なぜ複製するのか
  3.2 主体と追従者
  3.3 遅延が生む異常
  3.4 一貫性と可用性の選択
```

### 8.4 定義から実装へ降りる

```md
第1章 似た概念を区別する
  1.1 中心用語を定義する
  1.2 概念Aとは何か
  1.3 概念Bとは何か
  1.4 なぜこの区別が設計に効くのか

第2章 共有リソースと異常
  2.1 最小例で何が壊れるか
  2.2 読み取りと書き込みを分解する
  2.3 原子的な操作
  2.4 排他制御と待機条件

第3章 安全な抽象へ進む
  3.1 低レベル API の落とし穴
  3.2 型や契約で防げるミス
  3.3 メッセージによる分離
  3.4 実装選択の指針
```

## 9. 執筆チェックリスト

### 章を書く前

```md
章タイトル:
対象読者:
前提知識:
この章で解ける疑問:
この章で扱わないこと:
最初に出す失敗例または疑問:
中心となる用語:
中心となる図表:
最小コード例:
実務上の判断:
章末で回収する要点:
```

### 節を書く前

```md
この節の問い:
読者のありがちな誤解:
最初に定義する用語:
使う例:
例から導く一般化:
注意点:
次の節への接続:
```

### 推敲時

- 冒頭で読者像と到達点がわかるか。
- 技術名の羅列ではなく、問題から始まっているか。
- 用語が初出時に定義されているか。
- コード例の直後に読むポイントがあるか。
- 図表の前後に説明があるか。
- 正常系だけでなく、失敗例や限界があるか。
- 設計判断に必要な比較軸があるか。
- 章末のまとめが、章冒頭の問いに答えているか。
- 次章への接続があるか。

## 10. 避ける書き方

### API リファレンスの言い換えで終わる

避ける例:

```md
[API] は [機能] のための API です。第 1 引数に [値]、第 2 引数に [値] を渡します。
```

改善例:

```md
[API] は、[問題] を [考え方] で扱うための仕組みです。
ただし、すべての場面で使えばよいわけではありません。
[条件] では有効ですが、[別条件] では [危険やコスト] が生じます。
```

### ベストプラクティスだけを置く

避ける例:

```md
[設定] を有効にしましょう。
```

改善例:

```md
[設定] は、[経路] から [対象] を守るためのものです。
[失敗条件] が起きたときに [被害] を下げます。
属性名やコマンドを暗記するのではなく、何から何を守るのかを対応づけて理解します。
```

### 例外を隠す

避ける例:

```md
失敗したらリトライします。
```

改善例:

```md
失敗したように見えても、相手が処理したかどうかは区別できない場合があります。
そのため単純なリトライでは二重実行が起きる可能性があります。
安全にリトライするには、重複排除や冪等性の仕組みが必要です。
```
