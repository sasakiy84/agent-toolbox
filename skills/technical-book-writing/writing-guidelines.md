# 技術書執筆スキル

この文書は、質の高い技術解説を書くための実践ガイドラインです。特定の本文を模倣して写すためではなく、文体、情報の出し方、トピック設計、章構造、説明技法を再利用可能な「執筆スキル」としてまとめます。

## 1. このスキルの目的

このスキルの目的は、読者が「手順をなぞれる」だけでなく、「なぜその技術がそう設計されているのか」「どの場面で使い、どの場面で避けるのか」まで理解できる技術解説を書くことです。

目指す文章は、次の性質を持ちます。

- 読者像と到達点が冒頭で明確である。
- 用語、背景、問題設定、解決策、限界が順番に出てくる。
- コードや設定例が、概念の説明と分離せず、理解のために配置されている。
- 章の最後で、読者が何を理解したかを言語化して回収する。
- 実務上の判断に使えるトレードオフ、落とし穴、設計上の含意まで扱う。

## 2. 主要な説明パターン

質の高い技術解説に共通するのは、単に API や手順を説明するのではなく、読者が技術の位置づけを理解できるように「地図」を先に作る点です。地図には、読者の疑問、概念の分類、処理の流れ、失敗例、比較軸、運用上の判断基準などがあります。

この章では、特定の技術領域に固定せず、どの技術解説にも転用できる説明パターンとして整理します。

### 2.1 対話で誤解を解く型

読者が抱きそうな誤解や違和感を、章や節の入口に置く型です。

典型的な流れは次のとおりです。

1. 読者の素朴な理解を提示する。
2. その理解のどこが不正確かを指摘する。
3. 正しい定義や歴史的背景を説明する。
4. 小さなコード例で確認する。
5. 実務上、その理解がなぜ重要かを述べる。

向いている場面は、読者が「見た目から誤解しやすいもの」「既存コードの意図を読み解く必要があるもの」「仕様の背景を知らないと納得しにくいもの」を説明するときです。

悪い例:

```md
JSX は JavaScript の構文拡張です。Babel によって変換されます。
```

よい例:

```md
JSX を「React 用のテンプレート言語」と考えると、最初は理解しやすいかもしれません。
しかし、その理解のままだと、なぜ JSX の中で JavaScript の式を書けるのか、なぜ属性名が
HTML と微妙に違うのかを説明できません。JSX はテンプレートではなく、JavaScript の式として
UI の構造を表すための構文拡張です。まずは、次の JSX がどのような JavaScript に変換されるかを
見てみましょう。
```

ポイントは、結論を急がず、読者の誤解を学習の入口として使うことです。

### 2.2 体系化して関心事を分ける型

最初に領域全体を分解し、「この章では何を扱い、何を扱わないか」を丁寧に定義する型です。

典型的な流れは次のとおりです。

1. 技術領域が複雑化した背景を説明する。
2. 領域を大きな分類に分ける。
3. それぞれの関心事を列挙する。
4. 本書・本章で扱う範囲を宣言する。
5. 以後の章がその分類のどこに位置するかを示す。

向いている場面は、要素技術が多く、読者が個別の用語を同じ平面に並べて混乱しやすいテーマを扱うときです。

例:

```md
Web セキュリティを一枚岩として扱うと、Cookie、CORS、認証、XSS、TLS、CSP が同じ平面に並んでしまいます。
しかし、それぞれが守ろうとしている対象は異なります。そこで本章では、まず関心事を
「サーバー側で何を守るか」「ブラウザ側で何を隔離するか」「通信経路で何を保証するか」の
3 つに分けます。この分類を先に作っておくことで、後で登場する個別の仕組みを迷子にせずに
理解できます。
```

### 2.3 原理とトレードオフを比較する型

単一の正解を押しつけず、複数の選択肢を比較しながら設計判断へ導く型です。

典型的な流れは次のとおりです。

1. 現実のアプリケーションが抱える要求を提示する。
2. 既存の分類や単純な理解が崩れる理由を述べる。
3. 複数のモデルやアプローチを比較する。
4. それぞれの長所、短所、前提条件を説明する。
5. 「どれを選ぶべきか」ではなく「何を犠牲にして何を得るか」を言語化する。

向いている場面は、複数の実装方法や運用方法があり、読者が「どれを選べばよいか」ではなく「何を優先して選ぶか」を判断する必要があるときです。

例:

```md
キャッシュを導入すると、読み取りは速くなります。しかし、速くなることだけを見て採用すると、
今度はキャッシュとデータベースの整合性を誰が保つのかという問題が残ります。つまりキャッシュは
「遅い読み取り」を「同期の難しさ」に置き換える技術です。この置き換えが割に合うかどうかを、
アクセス頻度、許容できる古さ、障害時のふるまいから判断します。
```

### 2.4 定義から実装へ降りる型

似た用語を厳密に分け、抽象的なモデルから実装へ段階的に降りる型です。

典型的な流れは次のとおりです。

1. 混同されやすい用語を取り上げる。
2. 本書内での定義を明示する。
3. 状態遷移やモデルで抽象化する。
4. 小さな異常例を示す。
5. 低レイヤの仕組みを説明する。
6. 高レイヤの安全な API や設計指針に接続する。

向いている場面は、抽象概念と実装が密接で、用語の混同が後続の理解を壊しやすいテーマを扱うときです。

例:

```md
「並行」と「並列」は、日常的には同じ意味で使われることがあります。しかし本章では区別します。
並行性は、複数の処理を独立した進行中の活動として扱える性質です。並列性は、それらの処理が
物理的に同時に実行される性質です。この区別を先に置く理由は、スレッドを増やしても必ず高速に
なるわけではないことを、後で正確に説明するためです。
```

### 2.5 プロトコルと運用を接続する型

仕組み、手順、運用、失敗事例を分けずに接続する型です。

典型的な流れは次のとおりです。

1. そのプロトコルが解決する現実の問題を述べる。
2. 安全性だけでなく、相互運用性、性能、運用性も目標として示す。
3. プロトコルの手順を段階に分ける。
4. 各段階で何が保証され、何がまだ保証されないかを説明する。
5. 歴史的な攻撃や失敗を紹介し、設計の理由を補強する。
6. 最後に設定、実装、運用上の判断へ落とす。

向いている場面は、仕様を理解するだけでは不十分で、設定、運用、障害対応、互換性まで含めて判断する必要があるテーマを扱うときです。

例:

```md
TLS の目的は、単に通信を暗号化することではありません。クライアントが意図したサーバーと
話していること、途中で内容が改ざんされていないこと、異なる実装同士が同じ手順で通信できることも
同時に満たす必要があります。したがって TLS のハンドシェイクを読むときは、「どのメッセージで
鍵が決まるか」だけでなく、「どの時点で相手を信用できるようになるか」に注目します。
```

## 3. 章構造の基本テンプレート

技術書の各章は、次の順番で組み立てると安定します。

### 3.1 章タイトル

章タイトルは、扱う技術名だけでなく、読者が得る理解を含めます。

弱いタイトル:

```md
第4章 Cookie
```

強いタイトル:

```md
第4章 Cookie を安全に扱うための属性とブラウザの制約
```

弱いタイトル:

```md
第7章 useEffect
```

強いタイトル:

```md
第7章 useEffect で副作用をコンポーネントの外側と同期する
```

### 3.2 章の冒頭

章の冒頭では、次の 5 つを 800 字程度までで提示します。

- いま読者がどこにいるか。
- この章で扱う問題は何か。
- その問題が実務でなぜ重要か。
- この章で扱う範囲と扱わない範囲は何か。
- 章を読み終えると何が判断できるようになるか。

テンプレート:

```md
前章では、[前章の到達点] を見ました。しかし、[前章の方法] だけでは [新しい問題] を扱えません。
本章では、[中心トピック] を使って、この問題を [どの観点] から整理します。

最初に [用語またはモデル] を定義し、次に [最小例] で問題を再現します。その後、[仕組み] を説明し、
最後に [実務上の判断] をまとめます。本章の目的は、[技術名] の API を暗記することではなく、
[読者ができるようになる判断] です。
```

例:

```md
前章では、React コンポーネントが props と state から画面を計算することを見ました。しかし実際の
アプリケーションでは、画面の内側だけで完結しない処理が必ず出てきます。データ取得、購読、
タイマー、DOM の直接操作などは、React の外側にある状態とコンポーネントを同期する処理です。

本章では useEffect を、単なる「マウント時に実行する関数」ではなく、外部システムとの同期を
宣言するための仕組みとして整理します。最初に副作用という言葉を定義し、次に依存配列の意味を
小さな例で確認します。最後に、useEffect を使うべき処理と、使わないほうがよい処理を判断できる
ようにします。
```

### 3.3 節の構造

節は、次の 6 段階で書きます。

1. 問いを置く。
2. 用語を定義する。
3. 最小例を出す。
4. 仕組みを説明する。
5. 例外、落とし穴、限界を述べる。
6. 次の節への接続を書く。

テンプレート:

```md
#### なぜ [技術/概念] が必要なのか

[読者がすでに知っている方法] でも、[単純なケース] では問題ありません。
しかし、[条件] が加わると [失敗] が起こります。

ここで [技術/概念] が必要になります。[技術/概念] とは、[短い定義] です。
まずは次の例で、[失敗] がどのように起こるかを見ます。
```

### 3.4 章末のまとめ

章末のまとめは、単なる箇条書きではなく、章の冒頭で立てた問いに答える形にします。

弱いまとめ:

```md
本章では useEffect について説明しました。
```

強いまとめ:

```md
本章では、useEffect を「レンダリング後に何かを実行する API」ではなく、React の外側にある
システムとコンポーネントを同期するための仕組みとして見てきました。依存配列は実行タイミングを
気分で調整するためのものではなく、同期に使う値を React に伝えるための宣言です。

この理解に立つと、データの加工やイベントハンドラ内で完結する処理を useEffect に逃がすべきでは
ない理由も説明できます。次章では、この考え方をデータ取得に広げ、コンポーネントで非同期処理を
扱うときの設計を見ていきます。
```

## 4. 文体のルール

### 4.1 基本文体

本文は、原則として「です・ます」調か「だ・である」調のどちらかに統一します。

実務書、入門書、チーム向け教材では「です・ます」調が向いています。読者の理解を支える柔らかさを出しやすいためです。

理論寄り、仕様寄り、大学講義風の本では「だ・である」調が向いています。定義や主張を短く置きやすいためです。

混ぜてよいのは、次のように役割が違う場合だけです。

- 本文は「です・ます」調。
- 定義ボックスは「である」調。
- 対話文は口語。
- コラムは少しくだけた調子。

### 4.2 一文の長さ

一文は 40 から 80 字程度を基準にします。長くなる場合は、次のいずれかに分けます。

- 原因と結果で分ける。
- 前提と結論で分ける。
- 定義と例で分ける。
- 一般論と例外で分ける。

悪い例:

```md
キャッシュは読み取りを高速化するために使われる仕組みですが、データベースとの整合性を保つ必要があり、
更新時にはキャッシュを削除するのか更新するのか、TTL を使うのかなどを考える必要があります。
```

よい例:

```md
キャッシュは読み取りを高速化するための仕組みです。しかし、導入するとデータベースとの整合性を
保つ必要が生まれます。更新時にキャッシュを削除するのか、値を更新するのか、TTL に任せるのかを
先に決めておく必要があります。
```

### 4.3 接続語

技術解説では、接続語が論理の地図になります。次の接続語を意識的に使います。

- 定義する: 「ここでは」「本書では」「この章では」
- 理由を述べる: 「なぜなら」「その理由は」「背景には」
- 対比する: 「一方で」「これに対して」「しかし」
- 言い換える: 「つまり」「言い換えると」
- 例を出す: 「たとえば」「具体的には」
- 注意を促す: 「ただし」「なお」「ここで重要なのは」
- 先に進む: 「ここまでを踏まえて」「次に」「最後に」

使いすぎると説明が重くなるため、段落ごとに 1 つ程度を目安にします。

### 4.4 断定と保留

技術書では、断定すべきところと保留すべきところを分けます。

断定する:

- 用語の定義
- API の仕様
- コードの動作
- セキュリティ上危険な設定

保留する:

- 設計判断
- ライブラリ選定
- パフォーマンス評価
- 組織やチームに依存する運用

例:

```md
`useState` の更新関数は、次のレンダリングで使われる state を予約します。これは React の API として
決まっている動作です。

一方で、状態を `useState` で持つべきか、URL やサーバー状態として扱うべきかは設計判断です。
画面をリロードしても残すべき値なら、コンポーネントのローカル state に閉じ込めないほうがよい場合があります。
```

## 5. 情報の出し方

### 5.1 先に地図を渡す

複雑な章では、個別の API や設定に入る前に地図を渡します。

地図には次の種類があります。

- 領域の分類: サーバー側、クライアント側、通信経路
- 処理の流れ: 入力、変換、保存、出力
- 責務の分離: UI、状態、データ取得、永続化
- 時間の流れ: 接続前、接続中、接続後
- レイヤー: アプリケーション、ランタイム、OS、ハードウェア

例:

```md
認証認可を理解するには、先に登場人物を分けておく必要があります。本章では、ユーザー、
クライアントアプリケーション、認可サーバー、リソースサーバーの 4 つに分けます。
この分解をしておくと、アクセストークンが「誰のために」「誰へ向けて」発行されるのかを
混同せずに済みます。
```

### 5.2 用語は初出時に定義する

用語は、初出時に短く定義します。定義、直感的説明、例をセットにすると読者が迷いません。

テンプレート:

```md
[用語] とは、[短い定義] です。直感的には、[身近な言い換え] と考えるとよいでしょう。
たとえば、[具体例] が [用語] にあたります。
```

例:

```md
レースコンディションとは、複数の処理が共有リソースに並行してアクセスした結果、実行順序によって
結果が変わってしまう状態です。直感的には、「同じ値を見て、それぞれが別々に正しいつもりで更新する」
ことで起きる不整合です。たとえば、2 つのスレッドが同じカウンタを同時に 1 増やす処理が該当します。
```

### 5.3 例は最小から始める

最初の例に実務コードをそのまま出すと、読者は本質以外の情報に気を取られます。最初は、失敗や仕組みが見える最小例にします。

悪い例:

```tsx
function UserDashboard() {
  // 認証、キャッシュ、エラーハンドリング、ルーティング、表示制御が全部入った例
}
```

よい例:

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}
```

この最小例で「状態が変わると再レンダリングされる」ことを確認してから、非同期更新、親子コンポーネント、外部ストアへ進みます。

### 5.4 歴史は設計理由を説明するときだけ使う

歴史的経緯は、技術の必然性を説明するときに強力です。ただし、年表そのものが目的にならないようにします。

よい歴史の使い方:

```md
React が JSX を採用した理由を理解するには、当時のテンプレート中心のフレームワークと比較すると
見通しがよくなります。テンプレートに独自構文を増やすほど、HTML の中に小さな別言語が生まれます。
React はその方向ではなく、JavaScript の表現力を使って UI を記述する方向を選びました。
```

悪い歴史の使い方:

```md
2010 年に A が登場し、2011 年に B が登場し、2012 年に C が登場しました。
```

年表は、設計判断の流れが見える場合だけ使います。

### 5.5 図表は本文の代わりではなく、本文の圧縮に使う

図表は、次の用途に使います。

- 分類を一覧する。
- 処理の順序を示す。
- レイヤーの関係を示す。
- 比較軸を固定する。
- 状態遷移を示す。

図表の直前には「何を見るべきか」を書き、直後には「図から何がわかるか」を書きます。

例:

```md
次の表では、3 つの状態管理方法を「保存場所」「リロード後に残るか」「共有範囲」の観点で比較します。

| 方法 | 保存場所 | リロード後 | 共有範囲 |
| --- | --- | --- | --- |
| useState | コンポーネント内 | 消える | そのコンポーネント以下 |
| URL | ブラウザのアドレス | 残る | リンクを共有した相手 |
| サーバー | データベース | 残る | 権限を持つ利用者 |

この表から、検索条件のように共有可能であるべき状態は、`useState` だけに閉じ込めると扱いにくくなる
ことがわかります。
```

## 6. トピック設計

### 6.1 技術名ではなく、読者の判断単位でトピックを切る

章や節は、技術名の一覧ではなく、読者が実務で判断する単位で切ります。

弱い構成:

```md
第1章 useState
第2章 useEffect
第3章 useMemo
第4章 useCallback
```

強い構成:

```md
第1章 コンポーネントの中に閉じる状態を扱う
第2章 外部システムとコンポーネントを同期する
第3章 重い計算と参照の安定性を扱う
第4章 Hooks を使いすぎないための設計判断
```

API は章タイトルではなく、判断を支える道具として登場させます。

### 6.2 「なぜ今これを学ぶのか」を明示する

読者は、技術の重要性よりも順番に迷います。各章の冒頭で、前章からの必然性を書きます。

例:

```md
ここまでで、単一コンポーネントの状態は扱えるようになりました。しかし、実際の画面では複数の
コンポーネントが同じデータを必要とします。この章では、状態をどこに置くかという問題を扱います。
```

### 6.3 トピックは「背景、仕組み、実務」の三層で扱う

各トピックは、次の三層を揃えると厚みが出ます。

- 背景: なぜ必要になったか。
- 仕組み: どう動くか。
- 実務: どう使い、どこで避けるか。

例:

```md
#### SameSite Cookie

背景:
CSRF は、ブラウザがリクエスト時に Cookie を自動で付ける性質を利用する攻撃です。

仕組み:
`SameSite` 属性は、別サイトからのリクエストに Cookie を送るかどうかをブラウザに指示します。

実務:
通常のセッション Cookie には `Lax` または `Strict` を検討します。ただし、外部 ID プロバイダからの
リダイレクトや埋め込み用途がある場合は、単純に `Strict` にするとログインフローを壊すことがあります。
```

## 7. 説明技法

### 7.1 読者の誤解を先に言語化する

よい技術解説は、正しい説明だけでなく、読者がどこで間違えやすいかを先回りします。

テンプレート:

```md
[技術] を初めて見ると、[ありがちな誤解] のように見えるかもしれません。
しかし、この理解では [説明できない現象] を説明できません。
正しくは、[正しい見方] と捉える必要があります。
```

例:

```md
`useEffect` を初めて見ると、「レンダリング後に処理を実行するための場所」のように見えるかもしれません。
しかし、この理解では依存配列に何を書くべきかを説明できません。正しくは、`useEffect` は
コンポーネントが利用している外部システムとの同期を宣言する場所です。
```

### 7.2 失敗例から始める

抽象的な概念は、成功例より失敗例から入るほうが伝わりやすいことがあります。

例:

```md
トランザクション分離レベルは、名前だけを覚えても使えるようになりません。まず、分離が弱いと
どのような異常が起きるのかを見ます。次の例では、2 人の医師が同時に当直を外れようとした結果、
誰も当直に残らない状態が発生します。
```

この後に、読み取り、判定、書き込みがどの順序で並ぶかを表で示すと理解しやすくなります。

### 7.3 比較軸を固定する

複数の技術を比較するときは、比較軸を固定します。

悪い例:

```md
Redux は有名です。Context は簡単です。Zustand は軽量です。
```

よい例:

```md
ここでは状態管理の選択肢を、次の 4 つの軸で比較します。

| 観点 | Redux Toolkit | Context | Zustand |
| --- | --- | --- | --- |
| 更新ロジックの集約 | 強い | 弱い | 中程度 |
| 非同期処理との相性 | 高い | 自前で設計 | 中程度 |
| 再レンダリング制御 | 明示的 | 注意が必要 | 比較的容易 |
| 学習コスト | 高い | 低い | 中程度 |

この比較から、単に「小さいアプリなら Context」とは言えないことがわかります。更新ロジックが
複雑なら、画面数が少なくても専用の状態管理を入れる価値があります。
```

### 7.4 低レイヤと高レイヤを往復する

低レイヤの説明は、実務上の API に戻して終えると読者の理解が定着します。

例:

```md
CPU のアトミック命令は、読み取りと書き込みの間に他の処理が割り込めないようにするための
低レイヤの仕組みです。しかし、アプリケーションコードで毎回アトミック命令を直接扱うわけでは
ありません。通常は、ミューテックス、チャネル、スレッドセーフなコレクションなど、より高レイヤの
抽象を使います。低レイヤを学ぶ目的は、それらの抽象がどのような問題を隠してくれているかを
理解することです。
```

### 7.5 攻撃者、障害、利用者の視点を入れる

安全性や信頼性を扱う章では、通常の成功パスだけでは足りません。

視点を切り替えます。

- 攻撃者なら、どこを悪用するか。
- 障害が起きたら、どの前提が崩れるか。
- 利用者は、どの操作を自然に行うか。
- 運用者は、どのログやメトリクスを見るか。

例:

```md
CORS は、サーバーが「どのオリジンからのブラウザ読み取りを許可するか」を示す仕組みです。
攻撃者の視点で見ると、ここで `Access-Control-Allow-Origin: *` と資格情報付きリクエストを
不用意に組み合わせられれば、別サイトからユーザーのデータを読める可能性が生まれます。
そのため CORS の説明では、ヘッダの書き方だけでなく、何を許可しているのかを必ず言語化します。
```

## 8. コード例の書き方

### 8.1 コードは「差分」で学ばせる

大きな完成コードを一度に出すのではなく、差分で見せます。

手順:

1. まず動く最小コードを示す。
2. 問題を 1 つ発生させる。
3. 変更箇所だけを示す。
4. なぜその変更で直るかを説明する。
5. まだ残る問題を次の節へ渡す。

例:

```tsx
function SearchBox() {
  const [query, setQuery] = useState("");

  return (
    <input value={query} onChange={(event) => setQuery(event.target.value)} />
  );
}
```

説明:

```md
このコードでは、入力欄の値を React の state として管理しています。これだけなら問題ありません。
しかし、`query` を使って API を呼び出すと、キー入力のたびにリクエストが発生します。次に、
この問題をデバウンスで緩和します。
```

### 8.2 コードの直後に読むポイントを書く

コードを出したら、読者に「どこを見ればよいか」を示します。

例:

```md
注目するのは、`setCount(count + 1)` ではなく `setCount((current) => current + 1)` と書いている点です。
更新後の値が現在の state に依存する場合、関数を渡すことで、React が保持している最新の値に基づいて
次の state を計算できます。
```

### 8.3 実務コードに進む前に制約を書く

最小例は、現実の制約を省いています。省いたことを明示します。

例:

```md
ここでは説明を簡単にするため、エラーハンドリング、ローディング表示、リクエストのキャンセルは
省略しています。実際の画面では、少なくともこれら 3 つを追加する必要があります。
```

この一文があると、読者はサンプルコードを実務コードとして過信しません。

## 9. 注、コラム、脚注の使い分け

### 9.1 NOTE

NOTE は、本文の理解を助ける補足に使います。

例:

```md
> NOTE
> 本章では、ブラウザから送信される HTTP リクエストだけを扱います。curl やサーバー間通信では
> 同じヘッダでも意味が変わる場合があります。
```

### 9.2 WARNING

WARNING は、誤るとバグ、脆弱性、データ破壊につながる点に使います。

例:

```md
> WARNING
> JWT を localStorage に保存すると、XSS が起きたときにトークンを読み取られる可能性があります。
> 保存場所は、攻撃モデルとアプリケーションの要件を踏まえて決める必要があります。
```

### 9.3 コラム

コラムは、本文の主線から外れるが、理解を深める背景に使います。

使ってよい内容:

- 歴史的経緯
- 名前の由来
- 代替技術との関係
- 仕様策定の背景
- 実務でよくある逸話

使わないほうがよい内容:

- 本文に必要な定義
- 章の結論
- セキュリティ上の注意
- 手順の必須ステップ

### 10.1 基礎から実装へ進む章立て

  1.4 まとめ

第2章 言語と実行モデルを理解する
  2.1 値、参照、オブジェクト
  2.2 関数とクロージャ
  2.3 非同期処理とイベントループ
  2.4 後続のコードを読むために必要な考え方

第3章 宣言的な記述で構造を表現する
  3.1 なぜ専用の記法が必要なのか
  3.2 記法はどのように通常のコードへ変換されるか
  3.3 属性と子要素

- 個別ヘッダや属性は、守る境界の中に配置する。
- 「設定例」だけで終わらず、弱めると何が起きるかを書く。

## 12. よく使える段落パターン

### 12.1 誤解を修正する段落

```md
[技術] を [ありがちな理解] と捉えると、最初の説明としてはわかりやすいかもしれません。
しかし、その理解のままだと [説明できない現象] を説明できません。
本章では [技術] を [正しい理解] として捉え直します。
```

例:

```md
Context を「props のバケツリレーを避けるための道具」と捉えると、最初の説明としてはわかりやすい
かもしれません。しかし、その理解のままだと Context の値が変わったときに広い範囲が再レンダリング
される理由を説明できません。本章では Context を、コンポーネントツリーに値を配布するための仕組み
として捉え直します。
```

### 12.2 定義する段落

```md
本章では、[用語] を [定義] と呼ぶことにします。この定義は [一般的な用法との差分] を含みます。
あらかじめ定義を固定しておく理由は、後で [混同しやすい概念] と区別するためです。
```

### 12.3 トレードオフを述べる段落

```md
[手法A] は [利点] を得る代わりに、[負担] を引き受けます。
[条件] ではこの負担は小さいため、[手法A] は有効です。
一方で、[別の条件] では [負担] が支配的になるため、[手法B] を検討します。
```

例:

```md
楽観的ロックは、ロックを保持しないことで並行性を高める代わりに、競合が起きたときのリトライを
引き受けます。競合がまれな更新ではこの負担は小さいため、楽観的ロックは有効です。一方で、
同じレコードに更新が集中する場面ではリトライが支配的になるため、悲観的ロックやキューによる
直列化を検討します。
```

### 12.4 章末で回収する段落

```md
本章では、[中心概念] を [見方] として整理しました。
最初に [問題] を確認し、次に [仕組み] を見ました。
最後に、[実務判断] を行うための観点として [比較軸] を導入しました。

この章の要点は、[短い結論] です。次章では、この理解を前提に [次のトピック] を扱います。
```

## 13. 避けるべき書き方

### 13.1 API リファレンスの言い換えで終わる

避ける例:

```md
`useMemo` は値をメモ化するための Hook です。第 1 引数に関数、第 2 引数に依存配列を渡します。
```

改善例:

```md
`useMemo` は、レンダリングのたびに実行すると高くつく計算を、依存する値が変わるまで再利用するための
仕組みです。ただし、すべての計算に付ければ速くなるわけではありません。メモ化自体にもコストがあり、
依存配列を誤ると古い値を使い続ける危険があります。まずは、どの計算が本当に再利用に値するかを
測定できるようにします。
```

### 13.2 ベストプラクティスだけを置く

避ける例:

```md
Cookie には HttpOnly と Secure を付けましょう。
```

改善例:

```md
`HttpOnly` は、JavaScript から Cookie を読めないようにする属性です。XSS が起きたときにセッション
Cookie を直接盗まれるリスクを下げます。`Secure` は HTTPS の通信でのみ Cookie を送る属性です。
どちらも多くのセッション Cookie では有効にすべきですが、それぞれが防ぐ攻撃は異なります。
属性名を暗記するのではなく、どの経路から Cookie を守るのかを対応づけて理解します。
```

### 13.3 例外を隠す

避ける例:

```md
分散システムではタイムアウトしたらリトライします。
```

改善例:

```md
分散システムでは、タイムアウトだけでは相手が処理したかどうかを判断できません。リクエストが
届かなかったのか、処理は成功したがレスポンスだけ失われたのか、クライアント側からは区別できない
ためです。そのため、単純にリトライするだけでは二重実行が起きる可能性があります。安全にリトライ
するには、冪等性キーや重複排除の仕組みが必要になります。
```

## 14. 文章の品質基準

完成した章は、次の質問に答えられる状態を目指します。

- 読者は、なぜこの章を読む必要があるかわかるか。
- 読者は、章の中心概念を一文で説明できるか。
- 読者は、最小例を自分で動かせるか。
- 読者は、失敗例を見て何が問題か説明できるか。
- 読者は、似た技術との違いを比較軸つきで説明できるか。
- 読者は、実務で採用する条件と避ける条件を言えるか。
- 読者は、次に何を学ぶべきかわかるか。

## 15. 実際に書くときの短い手順

1. 読者像を 1 人に絞る。
2. その読者が抱く誤解を 3 つ書く。
3. 章の中心問いを 1 つ決める。
4. 用語を 5 つ以内に絞って定義する。
5. 最小の失敗例を作る。
6. 失敗を説明するモデルや図を作る。
7. 解決策を 1 つずつ導入する。
8. 比較表で選択肢を整理する。
9. 実務上の判断基準を書く。
10. 章冒頭の問いに答えるまとめを書く。

この順番を守ると、文章が「知っていることの列挙」ではなく、「読者の理解が進む道筋」になります。
