# Sasakiy Polish Issue

既存 issue を実装着手可能な粒度まで磨くときに使う。先に `$sasakiy-issues` を読み、`CHANGES.md` 判断が必要なら `$sasakiy-changelog`、git 操作が必要なら `$sasakiy-git` を使う。リポジトリの `AGENTS.md` と issue テンプレートを優先する。

## 目的

polish は、issue を単に読みやすくする作業ではない。実装者が追加確認なしに着手でき、レビュー時に完了判定できる状態にする作業である。複数周レビュー、致命/重要指摘の解消、必要なテンプレート項目の補完、完了条件具体化、`pending/` 退避、`CHANGES.md` 方針確定まで行う。

## ユーザーとの対話

polish-issue では、実装の実現性、スコープ、完了条件をユーザーと対話しながら固める。create-issue より踏み込み、実装者が迷わない状態まで具体化する。

まず自分でリポジトリを読み、分かることを確認する。ユーザーには、コードからは決められない判断だけを聞く。質問は一度に多くしない。作業が進む最小単位で 1-3 点ずつ聞く。

対話で必ず確認する観点:

1. **実現性**: 現在のコード、依存ライブラリ、CI、対応プラットフォームで実装できるか。
2. **スコープ**: この issue でやること、やらないこと、別 issue に切ること。
3. **互換性**: 後方互換のない変更か、利用者に見える変更か。
4. **テスト**: どのテストで完了を証明するか。実機や外部サービスが必要なら代替確認は何か。
5. **リリース影響**: `CHANGES.md`、ドキュメント、サンプル、CI、パッケージングに反映が必要か。
6. **完了条件**: 何を確認したら close できるか。

質問例:

- 「この issue は実装まで含めますか、それとも実現性調査で close しますか」
- 「この変更は後方互換のない `CHANGE` として扱いますか、互換ありの `UPDATE` ですか」
- 「この issue では API 変更まで含めますか、内部実装の整理だけにしますか」
- 「実機検証が必要な場合、完了条件にどの環境での確認を入れますか」
- 「未確定の設計判断は、この issue 内で決めますか、`pending/` に移しますか」

ユーザー回答を受けたら、issue 本文へ具体的に反映する。回答内容を会話のまま残さず、`目的`、`設計方針`、`完了条件`、`備考`、`pending` 理由などの適切なセクションへ整理する。

## 実現性確認

polish では「できそう」ではなく、実装の入口が見えている状態まで確認する。

- 対象シンボル、呼び出し元、設定、テストを grep 可能な名前で特定する。
- 既存の実装パターンや類似テストがあるか確認する。
- 依存ライブラリや外部 API の制約がある場合は、一次情報またはリポジトリ内の実コードで確認する。
- ワンライナー、少数行の POC、`rg` によるコード調査、既存テストの限定実行など、低コストで確認できることは、ユーザーに聞く前にエージェント側で可能な限り確認する。
- 低コスト確認で分かった事実、確認コマンド、確認できなかった理由は issue 本文または報告に残す。
- 実装に必要な順序を列挙する。
- テストできない部分がある場合は、その理由と代替確認方法を書く。
- 仕様や外部事情で実現性が判断できない場合は、`pending/` 移動または調査 issue 化を検討する。

実現性に疑義が残る場合は、issue を実装着手可能扱いにしない。疑義を `現状`、`設計方針`、`完了条件`、`備考` のどこかに明記し、ユーザーに確認する。

## 入力確認

- 対象 issue。
- 関連する open / closed / pending issue。
- `AGENTS.md`、`issues/0000-template.md`、`CHANGES.md`。
- 対象コード、テスト、設定、CI、ドキュメント。
- 必要なら関連コミットの本文まで読む。

## polish で必ず見る項目

- `Priority` と `優先度根拠` が一致している。
- `Created`、`Completed`、`Model`、`Branch`、`Polished` がテンプレートに合っている。
- `Branch` がある場合は、ユーザー指示またはリポジトリ固有の規約に基づいている。
- `目的` が実装内容ではなく、なぜ必要かを説明している。
- `現状` が実コード・実ファイル・実挙動に基づいている。
- `設計方針` が実装手順、責務分担、対象外を明確にしている。
- `完了条件` が検証可能で、テスト・CHANGES・ドキュメント・CI を含むべき場合に含んでいる。
- `解決方法` は未完了 issue では空または予定、closed issue では実際の対応内容になっている。

## 具体化の基準

- 関数名、型名、ファイル名、設定名、テスト名を grep 可能な形で書く。
- 行番号を書く場合は、実装着手時に再確認する前提を添える。
- データ型、状態遷移、アルゴリズム、変換処理など、文章だけよりコードの方が実装イメージを共有しやすい内容は、`設計方針` に短いコードスニペットを入れて具体化する。
- 「いい感じに」「適切に」「必要に応じて」だけで終わらせない。
- リポジトリ内に同種のパターンがある場合は、それに合わせる。
- 実装順序が重要な場合は番号付きで書く。
- 分割すべきものは別 issue として切り出す。
- 設計判断が未収束なら `issues/pending/` へ移動する理由を書く。

## 複数周レビュー

必要な場合は複数周レビューして磨く。

1. 致命的な欠落を見る: 実装不能、根拠なし、完了条件なし、スコープ過大。
2. 重要な曖昧さを見る: 対象外、テスト、CHANGES、互換性、リリース影響。
3. 表現を整える: 重複、冗長、古い行番号、矛盾、用語ゆれ。
4. 指摘が残る場合は本文へ反映し、再レビューする。

polish 完了と言うのは、少なくとも致命的・重要な指摘が残っていない状態を指す。軽微な表現改善だけを残して実装に進める場合は、その判断を本文か報告に残す。

## Polished フィールド

テンプレートに `Polished: YYYY-MM-DD` がある場合は、polish した最終日に更新する。最新日で上書きする。`Polished` がない場合は、勝手に追加する前に issue テンプレートに合わせる。

## CHANGES 方針

利用者が観測できる変更、互換性、バグ修正、CI/パッケージング影響がある場合は、issue 本文に `CHANGES.md` の種別と配置方針を書く。機能に直接影響しない変更は `### misc` の要否を判断する。最終差分だけを書く、という方針も明記する。

## pending と split

- 技術的に可能か未確認なら、まず検討・調査用 issue にする。
- 外部依存や設計判断待ちなら `issues/pending/` に移す。
- 1 issue が複数の独立変更を含む場合は、`issues/SEQUENCE` に従って別 issue を作る。
- メタ issue では、concrete issue 一覧、依存関係、tracked items、最終 close 条件を明確にする。

## 完了時

- Markdown がテンプレートのフォーマットに合っている。
- `Polished` が必要なら更新済み。
- `Branch` とファイル名が必要なら更新済み。
- `pending/` や `closed/` への移動が必要なら `$sasakiy-issues` と `$sasakiy-git` に従う。
- polish のコミットを作る場合は、issue ID と「磨き上げる」内容が分かる件名にする。
