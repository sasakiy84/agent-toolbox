# Sasakiy Plan

実装前に、要求、issue、機能案、大きめの修正を実装着手可能な計画へ整理するときに使う。計画は作業過程のメモではなく、実装者が追加確認なしに着手でき、レビュー時に完了判定できる状態を目指す。

## 使う場面

- 変更が複数ファイル、複数責務、公開 API、DB、設定、UI、CI、パッケージングにまたがる。
- 要求が曖昧で、目的、対象外、完了条件を整理しないと実装判断がぶれる。
- 既存 issue、レビュー指摘、障害調査、設計変更を実装可能な単位へ落とす。
- 影響範囲、互換性、検証方法、リリース影響を事前に合意する必要がある。

小さく明確な修正では、重い計画文書を作らず、作業前確認と短い実装方針だけで進めてよい。

## 最初に確認するもの

- `AGENTS.md`
- README、docs、plans、schema、migration、CI、ビルド設定
- 変更対象の近接コード、呼び出し元、公開 API、設定、データ構造
- 関連テスト、失敗ケース、境界値、過去の回帰テスト
- 関連 issue、closed issue、過去コミット本文

リポジトリを読めば分かることは、ユーザーに聞かずに確認する。ユーザーに聞くのは、目的、優先度、スコープ、互換性、受け入れ条件など、外から決めるべき判断に限る。

## ユーザーに確認する場合

質問は作業が進む最小単位で 1 点ずつきく。リポジトリの `AGENTS.md` に従い、選択肢には `A1`、`A2`、`B1`、`B2` のような記号を付ける。

各選択肢には、内容、メリット、デメリットを書く。推薦する選択肢がある場合は、記号のあとに `(Recommended)` を付ける。

## 計画に含める内容

計画には、目的、現状、設計方針、テスト方針、完了条件をかく。
完了条件は、red/green TDD の粒度で網羅性と具体性を述べる。
検討過程で出てきた案は「やらないこと」に書かず、関連する場所か末尾で別案として採用しなかった理由を書く。


## 具体化

- 関数名、型名、ファイル名、設定名、テスト名を grep 可能な形で書く。
- データ型、状態遷移、アルゴリズム、変換処理など、文章だけでは曖昧になる内容は短いコードスニペットで具体化する。ただし、わかりにくいデータやフィールド名については、説明やサンプルのコメントを書く
- 将来の再利用可能性だけを理由にした共通化を計画に入れない。
- 変数名の `ID`、`cls` や、関数名の `get` など、対象や責務が分からない汎用名を避ける。
- リポジトリ内に同種のパターンがある場合は、それに合わせる。
- 技術的に可能か未確認なら、まず調査計画にする。

## レビュー

計画を完了扱いにする前に、以下をサブエージェントでレビューさせる。

1. 致命的な欠落: 実装不能、根拠なし、完了条件なし、スコープ過大。
2. 重要な曖昧さ: 対象外、テスト、互換性、リリース影響、ユーザー判断待ち。
3. 表現の矛盾: 重複、冗長、古い行番号、方針変更後の不要文言、用語ゆれ。
4. 実装可能性: 低コストの `rg`、既存テスト限定実行、少数行の POC で確認できることを残していないか。

とくにテストの網羅性と命名についてレビューする。

もし変更箇所があった場合は、修正後に再度新しいサブエージェントにレビューさせる

## 文書化

- 大規模な変更では、リポジトリの規約がない限り、`plans/` 以下に `p0000_TITLE.md` のような計画ファイルを作る。
- 複数ファイルをまたぐ機能や利用者が参照する仕様では、必要に応じて `docs/` や README も更新対象に入れる。
- 計画だけで終わる作業では、確認したコマンド、確認できなかった理由、残るリスクを報告する。
