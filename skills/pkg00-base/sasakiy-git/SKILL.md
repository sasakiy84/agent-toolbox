# Sasakiy Git

git 操作を行うときに使う。リポジトリ固有の git・コミット規約がある場合はそれを優先する。日本語で書く。

## 基本方針

- 勝手にコミットしない。ユーザーからコミットを求められた場合、または issue 運用上コミットが明示されている場合だけコミットする。
- 全ての必要なテストが通らない限りコミットしない。
- 破壊的な git 操作をしない。`reset --hard`、作業ツリーを捨てる checkout/restore、強制 push などは、ユーザーが明示した場合だけ行う。
- 作業前後に `git status --short` で差分を確認する。
- 作業前から存在する未コミット変更は、明示的に依頼されない限り触らない・戻さない・コミットに混ぜない。
- ユーザーや他プロセスの差分を巻き戻さない。

## コミット前チェック

コミット前に以下を確認する。

- `git status --short` で意図したファイルだけが含まれている。
- issue 対応なら issue 本文の完了条件を満たしている。
- リポジトリで指定された format / lint / test が通っている。


## ブランチと同期

- ブランチ戦略はユーザー指示またはリポジトリの方針に従う
- 作業ブランチを最新化する必要がある場合は、まず `git status --short` を確認する。
- ローカルで不要に履歴を書き換えない。
- conflict が出た場合は、関係ファイルを読んで解決し、解決内容をコミット本文か報告に残す。

## PR
- タイトルは、なぜ変えるのかと、この変更で何がどう変わるのかを、1文で書く。理由と、挙動がどう変わるかが書いてあれば、レビュアーはタイトルだけで妥当性の見当が付く。
- 実装の手順をなぞらない。そのPRで新しく作った関数名やファイルパスを並べたタイトルは、diffを読むまで意味が分からない
- 症状を消すとだけ書かない。「warningを消す」は握り潰しとも読め、変更の性質が伝わらない。「findOneAndUpdateのnew: trueはdeprecatedなのでreturnDocument: afterを使う」のように、理由と置き換えの中身を書く
- 自分達が仕様を決めた物の挙動が理由なら、「〜に対応した」と自分達の変更として書く。「XがYするので」と原因を外に置く形は、Xが自分達で変えられない物の時だけに使う。自分達のコントロール範囲内の事柄を原因に置くと、範囲外のどうしようもない事のように読め、前提条件を誤読させる
- 実装の条件を網羅するより、解決する問題を具体的に書く。効果の大半を占める条件を書き、残りの条件は概要欄に任せる
- ユーザーに見えるbugの修正は、「<再現条件>で<症状>が起きる問題を修正」の形で書く。どう直したかは、概要欄の冒頭に置く
- optionを足す変更は、「<何を変えるoptionか> <option名>を追加」の形で書く。効く範囲の限定や既定値は、概要欄に書く
- 機能の変更は、注釈が無ければ、その機能が主に使われる画面での話として読まれる。それ以外の画面の挙動を変える時だけ、画面の名前で範囲を示す。画面の名前は、実装の語ではなく、ユーザーが見る名前で書く
- - 何を直すPRなのかを最初に書く。冒頭には、見出しを付けず、指示元や関連ページのURLと、位置づけを示す1〜2文を置く。bugに気付いた状況の説明を本題の前に長く置くと、状況の説明が本題に見え、本題の説明を邪魔する。コード全体に効く欠陥なら、気付いた特定の実行の話で始めず、経緯は起点へのリンクで足りる
- タイトル・概要欄・コメントは、直前に最新版を取得してから書き換える
  - タイトル・概要欄・コメントのように人間も編集する共有テキストは、他の人が並行して編集している前提で扱う。
  - 書き換える直前に最新版を取得し、自分が元にした版から変わっていない事を確かめる。変わっていれば、最新版の上に自分の変更を当て直す
  - 元に戻す時は、編集履歴で取り消す変更を確かめ、最新版からその変更だけを取り消す
- 機能を構成する複数のステップをまとめたPRでは、ステップを操作や処理の流れの順にリスト記法で1行ずつ並べる。各行には、何を追加し、それで何ができるようになるかを書く。model・module・fileの実装単位で割らない。判定条件の中身や記録の形式のような詳細は、ステップのリストの後の節に置く

## コミットメッセージ
- コミットメッセージは複数行書く
- PR の書き方を真似する

## リンクが壊れない書き方をする

概要欄、コメント、commit message等、GitHubで表示される文章の全てに当てはまる。

- `#1234` やURLの前後には、半角スペースを入れる。`#1234で直した` はリンクにならない。`(https://example.com/日本語のページ)。` は、`)。` までがURLに含まれる
- `#数字` は、issueとPRの番号にだけ使う。Dependabot alertのように別の番号体系を持つ物は、フルURLで書く。`#数字` で書くと、同じ番号の無関係なissueやPRへのリンクになる
- URLの日本語の部分は、percent-encodeせずに書く。encodeしたURLは、どのページへのリンクかを人間が読み取れない

## 禁止事項

- テスト未実行または失敗を隠したコミット。
- `--no-verify` によるフックスキップ。
- 関係ない差分の巻き戻し。
