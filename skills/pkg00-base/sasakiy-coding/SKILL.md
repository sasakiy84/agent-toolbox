# Sasakiy Coding

コードを実装・修正・レビューするときに使う。まずリポジトリの `AGENTS.md`、変更対象の近接コード、関連テスト、関連文書、ビルド・lint・test 設定を読む。リポジトリ固有の規約がこの skill と違う場合は、リポジトリ固有の規約を優先する。

## 作業開始前

- 変更対象ファイルの周辺コードを読む。同じ責務の既存実装、呼び出し元、公開 API、設定、データ構造を確認する。
- 関連テストを読む。既存の成功ケース、失敗ケース、境界値、回帰テストの有無を見る。
- README、docs、plans、schema、migration、CI、ビルド設定、package manager、formatter、linter を確認する。
- 対象が曖昧な場合は、エントリポイント、検索可能なシンボル、既存 issue やドキュメントから範囲を絞る。
- コードからは決められない仕様判断だけを、ユーザーへ確認する。

## 変更範囲

- 依頼された目的に直接関係する変更だけを行う。
- ついでのリファクタリング、フォーマット変更、命名変更、ファイル移動を混ぜない。
- public API、CLI、設定ファイル形式、データ構造、DB スキーマ、出力形式、互換性を変える場合は、影響範囲を確認してから進める。
- 作業中に別の問題を見つけた場合は、今回の変更に混ぜず、別提案または別作業として扱う。

## 実装品質

- 既存コードの命名、責務分割、エラー処理、テストの書き方に合わせる。
- 新しい抽象化は、実際の重複や複雑性を減らす場合だけ導入する。将来の再利用可能性だけを理由に共通化しない。
- 関数を細かく切りすぎない。意味的に 1 つの処理なら、長さより読みやすい構造を優先する。
- コードジャンプが増えるだけの wrapper 関数や wrapper class を作らない。
- 一般的すぎて対象や責務が分からない命名を避ける。`get`、`data`、`item`、`manager` のような名前は、責務が具体化されているか確認する。
- 定数や型エイリアスは、利用箇所から不必要に離さない。
- 一定以上の SQL、HTML、CSS、JavaScript は、インラインではなく専用ファイルで管理する。
- コメントは処理内容ではなく、理由、制約、互換性、外部 API の癖、過去の不具合回避を説明するために書く。
- CLI 用のスクリプトのファイル冒頭や、長い関数のブロックごとの処理にはコメントを書く。ただし、関数名などですでに表現されている情報は書かない
- secret、token、credential、個人情報をログやテストデータに含めない。
- エラーを握りつぶさない。利用者に見せる必要のない内部状態は、外部レスポンスでは適切に丸める。
- ただし、オーバーエンジニアリングにならないようにする。とくに例外処理、互換性の確保、テストの網羅性の担保は、それらが必要になる確率と現在のプロジェクトの成熟度（現在のコードベースは実装が始まったばかりなのか、本番運用しており安定稼働が求められているのか）を考慮して、必要最小限にとどめる。


## 型が使える言語

- 関数の引数と返り値には型を明示する。
- `any`、広すぎる型、安易な型アサーション、`ignore` で型エラーや lint エラーを回避しない。
- 外部入力、DB レコード、API response は境界で検証または型変換し、内部型と混ぜない。
- 更新可能なフィールドは `Pick` などで型に表す。
- HTTP API の payload 構築と保存処理は分ける。
- request / response の互換性、エラーケース、空入力、境界値を確認する。

## テスト

- テストは仕様書として読めるように書く。テスト名、入力、期待出力を明確にする。
- 1 ケースでは 1 つの振る舞いだけを検証する。
- 正常系だけでなく、境界値、空入力、異常系、既存バグの再発防止を必要に応じて追加する。
- 可能な限り、テストダブルを使わないようにする。まずは関数を純粋関数にして返り値をテストできないかを再検討する。モックは外部境界だけに使う。呼び出し回数の計測に意味がない限り、関数が呼ばれたことをテストしない
- 標準 API や DB 機能そのものではなく、アプリケーション仕様をテストする。
- 副作用のある処理は、temporary file 相当の機能などを使い、ホスト環境への影響を抑える。
- HTTP API は、可能ならサーバーやブラウザを起動せず、`Request` から `Response` を検証する。


## UI

- 要素同士が重なっていないことを確認する。
- 機能として関連する要素は近接させ、関連のない要素は適度に離す。
- 同じ意味の要素には同じ余白、同じ高さ、同じ幅を使う。
- 色だけに意味を持たせず、テキスト、アイコン、配置、状態表現も併用する。
- Tab、Enter、Escape、Ctrl/Cmd+Z などのキーボード操作を主経路として設計する。
- フォーカス、disabled、loading、エラー、空状態、長いテキスト、レスポンシブ幅で破綻しないか確認する。
